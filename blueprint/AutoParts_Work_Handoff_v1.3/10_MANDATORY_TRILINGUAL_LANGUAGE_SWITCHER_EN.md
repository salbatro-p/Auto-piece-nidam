# 10 — MANDATORY TRI-LINGUAL LANGUAGE SWITCHER, LOCALIZATION & RTL ADDENDUM (v1.2)

**Owner decision dated 2026-10-29: Binding requirement for BOTH applications, from their first respective releases.** This document overrides any older wording that merely suggests optional multilingual support. It supplements `09_MANDATORY_TWO_APP_ARCHITECTURE_EN.md`. **Phase 1 must fully implement and test this in AutoParts Business (tablet POS + owner phone). Phase 2 must fully implement and test it in the separate public AutoParts Shop (mobile + desktop + PWA).** Do not postpone language support to a later release or treat it as three static screenshots.

## L10-01 — Top-bar always-visible language switcher
- Place a clear, touch-friendly language selection control in the **top/header navigation** of **both applications**. The three choices are **العربية (AR) | Français (FR) | English (EN)**. Display readable native-language names and/or short codes; avoid ambiguous flag icons, because language is not nationality. Expose an accessible listbox/menu (or segmented control on roomy tablet/desktop). On compact phones keep the selector plainly discoverable in the top bar, not buried in settings or hidden behind owner-only permissions.
- Selector is available on login, Business POS, owner mobile dashboard, catalog, product create/edit/upload, inventory, receiving, counter sale, suppliers, reports, profile and system dialogs; and in V2 on Shop home, vehicle finder, search, product, cart, checkout, account, tracking, returns and support. Public guests must be able to switch language **before sign-in** and while checking out.
- On RTL screens place the control in a predictable top-bar position that does not cover back/navigation controls or barcode search. Use responsive layout. Language selection must work on actual tablet and mobile devices, including keyboard and screen-reader operation.

## L10-02 — Immediate switching, preference and workflow safety
- Selecting another language updates **the current page and global navigation immediately**, without logging out, creating a new session, discarding cart state, resetting active filters or losing unsaved forms/uploads, cashier sale drafts, and in-progress inventory documents. Where a locale route reload is required for SEO, preserve the user's safe workflow state and never duplicate an inventory/checkout mutation.
- Save an authenticated user's preferred UI language in the profile and apply on next sign-in across their own devices. For public guests persist the preference per browser/device with suitable privacy handling; expose an easily accessible choice. A shared cashier tablet must NOT leak the previous worker's personal language/account/session settings into another employee's session. Do not force a language change in one user's session onto other users or all devices.
- First-launch default: read explicit stored selection first, then device/browser language if supported, otherwise use **French (FR)** as a configurable pilot default, not a hardcoded fact about every Moroccan customer. Allow owner to configure default locale later. No critical workflow may become blocked based on UI language choice.

## L10-03 — Complete localization, not label-only translation
- Provide real, professionally reviewed **AR, FR, and EN** translation dictionaries for all visible product UI: page headings, menus, forms, placeholders, field help, validation errors, toast messages, confirmation dialogs, offline warnings, stock states, sale/return workflows, permissions messaging, dashboard labels and charts, user onboarding and help. V2 adds checkout, shipping, account creation, policies, order states, returns/refunds, customer notifications and transactional message templates.
- Support AR/FR/EN product **display names, descriptions, category labels, vehicle/fitment disclaimers and controlled vocabularies**, with a translatable content schema and back-office editor; support data import/export of localized fields and review/approval status. Preserve manufacturer brands, OEM numbers, GTIN/barcodes, part references, SKUs, engine IDs and VINs exactly as authoritative data, not translated text.
- Never silently fabricate missing technical descriptions, translations or verified vehicle compatibility with AI. If a translation is missing, fall back visibly to a reviewed source-language string, keep a `translation_missing` indicator for editors and report coverage by locale; safety-critical warnings must be translated and approved before that product/flow can be made public. Product compatibility is an evidence-based data field, not something translation can make 'verified'.
- Internationalize all client and server-generated messages with stable message identifiers, ICU-style interpolation/plurals, locale-specific date/number formats and proper pluralization. Do not use ad-hoc string replacements scattered across components. Install/validate fonts with Arabic glyph support **using legitimate font assets**, without shipping font files separately to the user.

## L10-04 — Arabic RTL and mixed-direction engineering
- Arabic mode is right-to-left for application layout, text flow, labels, navigation, pagination, drawers, tables, form alignment, modal placement, charts where appropriate and focus movement. French and English modes are left-to-right. Set `lang` and `dir` correctly at the document/root level and retest each component. Do **not** mirror product photographs, logos, barcodes, QR codes, numeric identifiers, chart data or the meaning of direction-specific icons.
- Use bidi isolation (`dir=auto`, `<bdi>` or equivalent) for dynamic mixed-script product names, alphanumeric references (OEM, SKU, VIN), prices, phone numbers, stock quantities and vehicle identifiers to avoid display corruption. Ensure copy/paste and scanner input preserve exact bytes, and that user-search behavior is not broken by display direction.
- Test mobile touch, high zoom, large text, contrast, keyboard navigation and screen readers. Target WCAG 2.2 AA for app-controlled interactive components and document exceptions.

## L10-05 — Search, numeric consistency and legal output
- Language switch changes **UI language only**; it must not change pricing, reservation state, tenant, warehouse scope, business permissions, stock counts, tax calculations or the identity of the part. Query by FR/AR/EN labels and reviewed aliases/transliteration where available, but exact OEM, SKU, EAN/barcode and numbers must match in every UI language.
- Store money precisely in **MAD** with exact decimals/minor units; locale only changes formatting. Show timestamps in business-approved `Africa/Casablanca`, with UTC at rest; preserve exact numerical quantity and unit conversions (`PCS`, carton quantities) in all languages. Make decimals parse safely when Arabic/French number formatting differs. Receipts, inventory exports, invoice drafts, printed labels, email/SMS templates and PDFs, where in scope, must explicitly use a selected locale and preserve numeric correctness; legal/accounting wording requires local review.
- In public V2, use localized indexable URLs where appropriate (for example `/ar/`, `/fr/`, `/en/`), stable canonical/hreflang metadata, localized titles and meta descriptions, language-aware search and route switching that retains the current product/vehicle when equivalent content exists. Never expose an internal draft or unlicensed fitment due to locale routing or fallback.

## L10-06 — Implementation contracts, performance and acceptance
- Build a shared tested `packages/i18n` (or equivalent) with typed translation keys, dictionaries, locale resolver, switcher component, RTL utilities, formatting helpers and locale-aware backend message templates. Reuse this in `apps/business` and `apps/shop` without allowing public clients to load private staff strings/data. Include extraction/coverage tooling; track approved vs missing translations for each release.
- Localization should not introduce significant render lag or unexpected full-page refresh on an internal transactional screen. Load locale bundles efficiently, minimize layout shift/flash of incorrect language, cache static dictionaries safely and profile switching on representative low-end tablet and Android hardware.
- Mandatory E2E scenarios: (1) tablet cashier switches FR→AR→EN mid-cart/draft sale with no lost values, wrong totals or duplicate sale; (2) owner phone switches locales during new-product photo upload + 10-PCS receiving; (3) RTL OEM/GTIN, Arabic and Latin mixed search results copy correctly; (4) logout and employee switch on shared tablet does not leak personal preferences/session; (5) V2 guest switches locale on product→cart→checkout→order tracking preserving cart and completed order; (6) EN/AR/FR users can navigate independently without affecting one another; (7) all three language dictionaries pass coverage and critical-message reviews; (8) print/PDF/email receipts and dates/prices remain mathematically identical across locales; (9) accessibility and no major header overflow on portrait mobile/landscape tablet; (10) no public leakage of private content via localized route or fallback.
- **STOP-SHIP / NOT DONE:** any of the three language options absent in the visible top navigation of either released app; untranslated blocking dialogs or errors in a critical path; broken RTL; corrupted OEM/barcode; loss/duplication of stock/checkout mutations on language switch; inaccessible selector; missing safety-critical public translation; unknown/unreported localization coverage. Report PASS/FAIL/NOT TESTED per app, screen group, device and locale, with screenshots/video and test logs.

## Delivery artifacts
- Actual tested global header switcher for both apps, AR/FR/EN screenshot matrix per screen class, localized message catalog and product translation schema, per-language content coverage report, E2E regression suite, mixed-direction and accessibility checks, locale-aware PDF/receipt/notification tests where applicable, and measured switch/render performance.
- Complete V1 Business locales **in Phase 1**. In Phase 2 implement Shop locales while preserving all existing Business locale functionality, and run cross-app regression tests. Document any unfinished translation as `NOT READY`, not a hidden post-launch TODO.
